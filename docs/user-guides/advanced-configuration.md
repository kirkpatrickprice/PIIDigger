# Advanced Configuration User Guide

## Overview

By default, `piidigger` scans every available drive/mount, every supported file type, every supported archive, and every registered PII data type. That's a reasonable starting point, but many times a narrower scan is needed — a specific folder, a specific PII type, or a network share you don't want to touch.

Configuration files let you control all of that without long command lines. PIIDigger reads settings from a [TOML](https://toml.io/) file, validates them, and uses them for the scan. This guide covers how to generate, edit, and validate a configuration file, what each setting does, and how to configure PIIDigger for a handful of common scenarios.

## Prerequisites

### System Requirements
- PIIDigger installed (see [Installation Guide](installation.md))

### Knowledge Requirements
- Basic PowerShell or Linux/macOS shell navigation
- Basic familiarity with TOML syntax (`key = "value"`, `[section]` headers, `["list", "of", "values"]`)

### Required Files/Data
- None — the config file is generated by PIIDigger itself; you edit it from there.

## Getting Started

### Generate a configuration file

```powershell
# Write a default config to .\piidigger.toml
piidigger config generate
```

This writes a fully-populated TOML file with every setting at its built-in default. It refuses to overwrite an existing file:

```
Error: 'piidigger.toml' already exists.  Delete it or choose a different path.
```

To write to a different path (useful for keeping multiple named profiles), pass a filename:

```powershell
# Write a named profile instead of the default piidigger.toml
piidigger config generate finance-share.toml
```

Open the generated file and edit the values you need — there's no need to touch settings you want left at their default.

### Validate a configuration file

Before running a long scan, check that your edits are well-formed:

```powershell
# Validate the configuration file
piidigger config validate piidigger.toml
```

A valid file reports:

```powershell
# Successful validation
'piidigger.toml': OK
```

An invalid file explains exactly what's wrong — including a suggestion when a setting name looks like a typo:

```powershell
# Unsuccessful validation
Error: invalid configuration in piidigger.toml:
- Unknown setting 'archives.enable'. Did you mean 'archives.enabled'?
```

`validate` also catches a TOML footgun that's easy to hit by hand: in TOML, a `key = value` line written *after* a `[section]` header becomes part of that section, even if you meant it as a top-level setting. `piidigger config validate` detects this and tells you to move the line above the first `[section]` header. If you run into this, it's usually simplest to run `piidigger config generate` again and copy your values into the fresh template, which already has the ordering right.

If a validate run doesn't pass, the same errors will stop a scan started with `-f`/`--config`, so it's worth running `validate` after every edit.

### Running a scan with your configuration

```powershell
# Explicit path
piidigger scan -f piidigger.toml

# Or just run piidigger from the folder containing piidigger.toml — it's
# picked up automatically, no flag needed
piidigger
```

```powershell
# Ignore any config file in the current directory and use built-in defaults
piidigger scan -d

# Skip archive scanning for just this run, regardless of what the config says
piidigger scan --no-archives
```

## Configuration Reference

All settings live in one TOML file. Root-level settings must appear *above* any `[section]` header (see the TOML footgun note above).

### Root-level settings

| Setting | Default | Description |
|---|---|---|
| `include_exts` | `["all"]` | File extensions to scan (e.g. `[".pdf", ".docx"]`). `["all"]` means every extension with a registered file handler. |
| `include_mime` | `["all"]` | MIME types to scan, checked in addition to `include_exts` (see note below). `["all"]` means every MIME type with a registered handler. |
| `data_handlers` | `["all"]` | Which PII types to look for (e.g. `["pan"]`, `["email"]`). `["all"]` runs every registered data handler. |
| `performance` | `"balanced"` | Worker process count preset. `"fast"` = one worker per logical core (e.g. a Hyper-Threaded 8-core Intel CPU has 16 logical cores), `"balanced"` = ~75% of physical cores, `"slow"` = a single worker. |
| `default_timeout_seconds` | `30` | Per-task deadline (1–600s). A worker that doesn't finish a single directory/file/archive-member task within this window is terminated and replaced; the task is recorded as timed out. This is not an overall scan time limit. |
| `local_files_only` | `true` | Skip OneDrive/Dropbox files that are cloud-only placeholders (not downloaded to disk), so a scan doesn't force megabytes of downloads. See the Google Drive scenario below — this check does **not** cover Google Drive. |
| `admin_check` | `true` | If not running elevated, prompt to confirm before scanning (a non-admin scan may not be able to read every file). The scan will continue in 10 seconds with no user input.  Set `false` to skip the prompt and continue automatically; it's ignored automatically anyway when not running from an interactive terminal. |
| `log_file` | `"logs/piidigger.log"` | Path to the run's log file. The parent folder is created if missing. |
| `log_level` | `"INFO"` | Standard Python logging level: `DEBUG`, `INFO`, `WARNING`, `ERROR`, or `CRITICAL`. |

**`include_exts` and `include_mime` are OR'd together, not AND'd.** A file is scanned if it matches *either* list. That means restricting only `include_exts` while leaving `include_mime = ["all"]` has no effect — the untouched MIME list still matches everything. If you want extension-based filtering to actually restrict the scan, either leave MIME detection aside entirely (it's best-effort and depends on `puremagic` being installed) and just know both lists need to be narrowed together, or restrict `include_mime` too. In practice, the simplest approach is to only ever edit one of the two and set the other to an empty list `[]` so it can't silently widen the match back to "all":

```toml
include_exts = [".pdf", ".docx", ".xlsx"]
include_mime = []
```

### `[start_dirs]` and `[exclude_dirs]`

These are the two settings that differ by operating system, so the same config file works on Windows, macOS, and Linux — each is a TOML table keyed by `windows`, `macos`, and `linux`; PIIDigger picks the key matching the OS it's running on and ignores the others.

```toml
[start_dirs]
windows = ["all"]
macos = ["/"]
linux = ["/"]

[exclude_dirs]
windows = ["C:/Windows", "C:/Program Files (x86)", "C:/Program Files"]
macos = ["/dev", "/etc", "/usr/bin", "/System", "..."]
linux = ["/boot", "/dev", "/proc", "/sys", "..."]
```

- `start_dirs`: folders to scan. `["all"]` on Windows expands to every drive letter present at scan time (`C:\`, `D:\`, …). On macOS/Linux, `/` scans the whole filesystem. Every `start_dirs` entry must exist on disk — `config validate` and `scan` both fail fast if one doesn't.
- `exclude_dirs`: folders to skip entirely, along with everything under them, on all operating systems — this is how the built-in defaults avoid wasting time on low-value folders like OS folders. Entries starting with `*` are suffix-matched (e.g. `"*/.vscode-server"` matches that folder name anywhere); everything else is a prefix match against the resolved path. Unlike `start_dirs`, an `exclude_dirs` entry does **not** need to exist — excluding a drive or folder that isn't currently present (e.g. an unmounted Google Drive letter) is fine and has no effect.

**Do not put a trailing slash on an `exclude_dirs` entry.** `"C:/Windows"` correctly excludes everything under `C:\Windows`. `"C:/Windows/"` (trailing slash) does **not** — the extra slash breaks the prefix match and the exclusion silently does nothing. All the built-in defaults follow this rule; keep your own entries consistent with them.

**A note about Windows paths:** As a restriction from the TOML format, the usual back-slash (e.g. `C:\Windows`) will not be interpreted correctly.  Either use a double back-slash (`C:\\Windows`) or a front-slash (`C:/Windows`).  Either option will be read correctly by PIIDigger. Use of a single back-slash will produce the following error when validating the configuration:

```powershell
# Use of a single back-slash in TOML configuration
piidigger config validate
Error: invalid TOML in piidigger.toml: Unescaped '\' in a string
```

### `[results]`

| Setting | Default | Description |
|---|---|---|
| `path` | `"piidigger-results"` | Folder where output files are written (created if missing). |
| `formats` | `["all"]` | Output formats to produce. Valid values: `"csv"`, `"json"`, `"text"`, or `["all"]` for all three. |

Output filenames are generated automatically as `<hostname>-<YYYYMMDD-HHMMSS>.<ext>`, so repeated runs never overwrite each other.

### `[archives]`
See [Archive Handling](archive-handling.md) for additional details on how PIIDigger handles archive file formats.

| Setting | Default | Description |
|---|---|---|
| `enabled` | `true` | Whether to look inside archive files at all. |
| `formats` | `["all"]` | Archive types to open. Valid values: `"zip"`, `"7z"`, `"tar"` (covers `.tar`, `.tgz`, `.tar.gz`, `.tbz2`, `.tar.bz2`, `.txz`, `.tar.xz`), or `["all"]`. |
| `max_depth` | `1` | Reserved for future nested-archive support (an archive inside an archive). **Currently has no effect** — a `.zip`/`.7z`/`.tar` found inside another archive is always skipped, regardless of this value. |
| `max_members` | `10000` | Stop enumerating an archive after this many members. Helps prevent against some archive-based denial of service attacks |
| `max_member_uncompressed_size_mb` | `512` | Skip any single archive member larger than this uncompressed. Also used as part of a 1000:1 compression-ratio check that rejects likely zip bombs. |
| `max_total_uncompressed_size_mb` | `8192` | Stop pulling more members from one archive once their combined uncompressed size passes this limit. |

These limits also implicitly protect against path-traversal members (`../`) and encrypted members, both of which are always skipped and logged, independent of any setting.

### Discovering valid values

Rather than guessing at handler/extension names, ask PIIDigger directly:

```powershell
piidigger inspect datatypes      # valid data_handlers entries (e.g. pan, email)
piidigger inspect filetypes      # valid include_exts / include_mime entries
piidigger inspect archivetypes   # valid archives.formats entries
```

## Common Scenarios

### Scan for only specific PII types

To look for credit card numbers only, and skip email address matching entirely:

```toml
data_handlers = ["pan"]
```

Run `piidigger inspect datatypes` to see the full list of registered handlers before picking names — an unrecognized name in `data_handlers` fails validation with the list of known handlers.

### Limit scanning to specific source paths

Rather than scanning every drive, point `start_dirs` at just the folders you care about. Because `start_dirs` is OS-keyed, only fill in the key for the OS you're actually running on — the others can stay as-is or be emptied:

```toml
[start_dirs]
windows = ["D:/Shared", "C:/Users/Public/Documents"]
macos = ["/Users/Shared"]
linux = ["/srv/shared"]
```

Every path listed must exist — `piidigger config validate` will catch a typo'd or unmounted path before you burn time on a scan that immediately fails.

### Exclude cloud-sync drives (e.g. Google Drive on `G:\`)

`local_files_only = true` (the default) only recognizes OneDrive and Dropbox placeholder files on Windows — it has no way to detect Google Drive's sync state. If Google Drive for Desktop is mounted as `G:\`, the safest way to keep a scan from pulling every file down through that mount is to exclude the drive outright:

```toml
[exclude_dirs]
windows = ["C:/Windows", "C:/Program Files (x86)", "C:/Program Files", "G:"]
```

Note the entry is `"G:"` — **no trailing slash and no backslash** — following the same rule as the other `exclude_dirs` entries above. `"G:/"` would not exclude anything under that drive.

**NOTE:** From our own testing, it *appears* that files that have actually been downloaded from Google Drive are physically present on the file system in an OS "temp" folder -- e.g. `C:/Users/<usesrname>/APPDATA/...`.  By default, PIIDigger will scan those because they're present on the drive.  By excluding the `G:` drive as described above, you can avoid downloading all files from Google Drive while still scanning those that have already exist on the file system.

If you only want to exclude one folder inside Google Drive rather than the whole mount, exclude that folder specifically instead:

```toml
windows = ["G:/My Drive/Personal"]
```

### Choose output formats

To produce only a CSV for import into a spreadsheet, skip JSON and plain text, and write it to a specific folder:

```toml
[results]
path = "C:/Scans/2026-Q3"
formats = ["csv"]
```

### Disable or tune archive scanning

To skip archives entirely for every run made with this config file:

```toml
[archives]
enabled = false
```

For a one-off run where you don't want to edit the file, use the flag instead:

```powershell
piidigger scan -f piidigger.toml --no-archives
```

To keep archive scanning on but guard against runaway processing on a share with very large or deeply-compressed archives, tighten the limits:

```toml
[archives]
enabled = true
formats = ["zip"]
max_members = 2000
max_member_uncompressed_size_mb = 128
max_total_uncompressed_size_mb = 2048
```

## Troubleshooting

### `config validate` reports "Unknown setting"

The setting name doesn't exist. If PIIDigger can guess what you meant, it tells you (`Did you mean '...'?`). Otherwise, run `piidigger config generate` to a new file and compare it against yours — a renamed or removed setting from an older version is the most common cause.

### `config validate` reports "Unexpected keys found inside [section]"

A root-level setting (like `log_level`) was written *after* a `[section]` header in the TOML file, so the TOML parser absorbed it into that section instead of treating it as top-level. Move the flat settings above the first `[start_dirs]`/`[results]`/`[archives]` header, or regenerate the template and re-apply your edits.

### `config validate` reports "Error: invalid TOML in piidigger.toml: Unescaped '\' in a string"

A single back-slash was used in a Windows path, contrary to the TOML specification.  Replace it with either a front-slash (`/`) or a double black-slash (`\\`).  Re-run `piidigger config validate`.

### `scan` fails with "start directory does not exist"

An entry in `start_dirs` (for your OS) points to a path that isn't there — often a drive letter that isn't mounted, or a typo. Fix or remove the entry and re-run `piidigger config validate`.

### An `exclude_dirs` entry doesn't seem to work

Check for a trailing slash or backslash — see the note under `[start_dirs] and [exclude_dirs]` above.
